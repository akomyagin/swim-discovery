# swim-discovery — PLAN

## Видение

`swim-discovery` — учебная реализация **service discovery на gossip-протоколе**
(мини-Serf / мини-Consul membership): узлы находят друг друга и детектят отказы
**без центрального координатора**, обмениваясь слухами по SWIM-подобному
протоколу. Каждый узел держит собственный, со временем сходящийся
(eventually consistent) список членов кластера — кто жив, кто под подозрением,
кто мёртв.

Цель — **искренняя техническая сложность и обучение**, не продукт. Это первая
распределённая система в портфеле; экономика не оценивается, бюджет $0, внешних
сервисов и Docker нет — самодостаточные Go-бинари, эмулирующие кластер на
localhost.

Три темы, ради которых проект делается:

1. **Gossip-протоколы.** Информация о членстве расходится по кластеру эпидемией
   слухов (piggyback на обычном probe-трафике), а не через центральный реестр.
2. **Failure detection под ненадёжной сетью.** Наивный «пингуй всех напрямую»
   даёт **false positives** при потере пакетов: потерялся *твой* пакет к узлу —
   и ты ошибочно счёл живой узел мёртвым. SWIM это лечит **indirect probing**.
3. **Eventual consistency.** Списки членов на разных узлах никогда не
   согласованы мгновенно; они сходятся. Конфликты слухов разрешаются по
   incarnation-номерам.

## Почему это не тривиальная обёртка

SWIM специально спроектирован против false positives при детекции отказов в
условиях packet loss. Если прямой ping не получил ack, узел **не** объявляет
цель мёртвой — он просит K случайных посредников пропинговать цель от своего
имени (indirect probe). Живой узел объявляется мёртвым только если и прямой, и
все косвенные пинги молчат, **и** истёк suspicion-таймаут без опровержения.
Наивная реализация «пингуй всех» ломается ровно там, где начинается реальная
сеть с потерей пакетов — а честно оттестировать это тяжелее, чем кажется.

## Архитектура (верхнеуровнево)

```
   несколько процессов на localhost, каждый — один узел на своём UDP-порту
   (127.0.0.1:7947, :7948, :7949, …); центрального координатора НЕТ

   ┌──────────────────────── один узел ────────────────────────┐
   │                                                            │
   │  probe-цикл (Этап 1,3,4)         gossip-цикл (Этап 2)       │
   │  ─ раз в интервал берёт           ─ на каждом сообщении     │
   │    случайного члена, шлёт Ping      piggyback-ит дельты     │
   │    ─нет Ack→ PingReq K соседям      членства (Update[])     │
   │    ─молчат→ Suspect                                         │
   │    ─таймаут→ Dead                                           │
   │            │                                │              │
   │            ▼                                ▼              │
   │   ┌──────────────────┐         ┌───────────────────────┐   │
   │   │ member.List      │◀────────│ merge по (Incarnation, │   │
   │   │ (локальный view) │ changed │  State): выше инкарн.  │   │
   │   │ map[ID]*Member   │────────▶│  побеждает; при равной │   │
   │   └──────────────────┘ re-gossip Dead>Suspect>Alive    │   │
   │            │                   └───────────────────────┘   │
   │            ▼                                                │
   │   protocol.Encode/Decode   (Ping/Ack/PingReq + Update[])   │
   │            │                                                │
   │            ▼                                                │
   │   transport.Transport  ← порт, подменяемый в тестах        │
   │      ├─ UDP     (прод: net-сокет на localhost)             │
   │      └─ Fake    (тесты: управляемая потеря/задержка)       │
   └────────────────────────────────────────────────────────────┘
```

Ключевая абстракция — **порт `transport.Transport`**. Прод-адаптер — реальный
UDP-сокет; тестовый — in-memory симулятор сети с управляемой потерей пакетов и
задержкой. Именно он делает false-positive-сценарии детерминированными.

## Скоуп MVP

- Модель узла + локальный membership-список с merge по incarnation-номерам.
- Прямой (direct) ping/ack failure detection поверх UDP на localhost.
- Gossip-рассылка дельт членства (piggyback на probe-трафике).
- **Indirect probing** (PingReq к K случайным посредникам) — защита от
  false positive при потере именно твоего пакета.
- Suspicion-механизм с таймаутами: alive → suspect → dead, с опровержением
  через более высокий incarnation.
- Тестовый симулятор сети (fake transport) с управляемой потерей/задержкой +
  CLI для наблюдения за сходимостью кластера.

Вне MVP (см. `POST_MVP_PLAN.md`): TLS между узлами, реальная многомашинная сеть
за пределами localhost, произвольные метаданные узла (теги/сервисы) в стиле
Consul, компактный бинарный wire-формат.

## Этапы

| Этап | Содержание | Ключевая мина |
|---|---|---|
| 0 | Скелет: модуль, пакеты-заглушки, CLI-заглушка, `go build`/`go vet` чисто | — |
| 1 | Модель узла + membership-список + direct ping/ack поверх UDP (localhost) | merge-precedence по incarnation |
| 2 | Gossip-рассылка дельт членства (piggyback) | сходимость без штормов |

| 4 | Suspicion-механизм с таймаутами (suspect→dead, опровержение) | гонки таймеров, refute |
