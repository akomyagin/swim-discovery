## 2. Техдолг — с триггерами пересмотра (актуальный на конец Этапа 5)

### Закрыто Этапом 5 (явным решением, зафиксировано в
`docs/TECHNICAL_PLAN.md`, раздел «Этап 5», и в плане `docs/plans/stage-5-network-sim-cli.md` §1-2)

- **`Clock` (suspicion) vs transport-delay** — решено окончательно: НЕ
  делятся. Delay в `transport.Fake` — на wall-clock (`time.AfterFunc`), не
  через инжектируемый `fakeClock`. Обоснование в TECHNICAL_PLAN и плане §1.
  Триггер пересмотра: тест, которому нужен один `Advance` на delay и
  suspicion одновременно (пока такого нет).
- **Eviction Dead-узлов** — решено НЕ вводить в Этапе 5. Инвариант «из
  `members` ничего не удаляется» остаётся цел. Это решение **переносит**, не
  закрывает, техдолг Этапов 2-4 (`PendingGossip`'s `*l.members[id]`,
  вечное пробитие Dead-узлов) — см. ниже, триггер не изменился.

### Остаётся открытым (унаследовано с Этапов 2-4, не тронуто Этапом 5)

- **`internal/member/member.go`, `PendingGossip`, `*l.members[id]`** без
  проверки наличия ключа — держится на инварианте «из `members` ничего не
  удаляется». Триггер: появление eviction (явно отложено дважды подряд —
  Этап 4 и Этап 5 — теперь это самостоятельная будущая задача со своими
  развилками, не «заодно» какого-то другого Этапа).
- **`probeOnce` продолжает пробить Dead-узлы вечно** без eviction — шумно
  («marking suspect» в логе на каждый неудачный опрос), но функционально
  безвредно (`Merge`'s precedence гасит повторный переход). Тот же триггер,
  что выше — решать вместе с eviction.
- **Бюджет ретрансляций замораживается на `len(members)` в момент `Merge`**
  (с Этапа 2) — не пересчитывается позже. Не наблюдалось на практике.

### Новое, найдено независимым ревью Этапа 5 (низкая критичность, осознанно
не исправлено)

- **`internal/transport/fake.go`, delayed-delivery `time.AfterFunc` без
  реестра для `Stop()`.** Каждый отложенный пакет — отдельный таймер +
  горутина, которая блокируется на `dst.inbound <- pkt`, если буфер
  получателя полон (64 слота) и получатель не читает. На масштабе тестов
  (единицы-десятки пакетов, delay 10-50мс) безвредно — таймеры отрабатывают
  и собираются GC, `<-dst.done` защищает от паники на закрытый эндпоинт.
  **Триггер пересмотра**: тест с большим объёмом задержанных пакетов на
  намеренно не читающего получателя (нагрузочный/долгоиграющий сценарий) —
  тогда завести реестр таймеров с `Stop()` в `Close`, аналогично паттерну
  suspicion-таймеров из Этапа 4.
- **Partition проверяется в момент `Send`, не в момент отложенной доставки.**
  Пакет, отправленный до `Partition`, но ещё не доставленный (в полёте под
  delay), доставится даже если после отправки цель партиционировали. Это
  осознанно смоделировано как «уже был в проводе, когда случился разрез» —
  не баг, но недокументированная асимметрия (partition/drop-rate действуют
  только на решение в момент `Send`, delay может «пережить» их дальнейшее
  изменение). Пересмотреть, если появится тест, которому важно, чтобы
  partition обрывал уже летящие пакеты.

### Исправлено в цикле фиксов Этапа 5 (для справки — не открытый техдолг)

- CLI (`cmd/swim-discovery/main.go`): лишний позиционный аргумент после
  подкоманды (опечатка во флаге без `-`) раньше молча проглатывал все
  следующие флаги (`flag.Parse` останавливается на первом non-flag токене);
  теперь `fs.NArg() > 0` после `Parse` завершает процесс с явной ошибкой.
- `FakeNetwork.Partition`: убрана лишняя ветка `if id == 0 { delete } else
  { assign }` — map и так возвращает 0 для отсутствующего ключа, разделение
  было избыточным.
- Doc-комментарий `FakeNetwork` уточнён: детерминизм («replays exactly»)
  гарантирован для потока одного отправителя на линк, не глобально при
  нескольких горутинах, конкурирующих за розыгрыш RNG на одном линке.

Дополнения, накопленные на Этапе 5:

- **Fable-агент может упасть с 403 (authentication/authorization) ещё до
  единой правки** — не путать с содержательным отказом по safety-классификатору
  (там обычно текстовый отказ, а не HTTP-код). Диагностика: проверить
  `git status`/`git diff --stat` сразу после сбоя — если рабочее дерево
  пустое, это транспортный/инфраструктурный сбой, не связан с задачей;
  решение — просто перезапустить тот же Agent-вызов с тем же промптом.
  На Этапе 5 сработало со второй попытки без изменений в промпте.
- **Фоновый субагент может завершить турн, не дождавшись собственного
  фонового bash-процесса** (кодер запустил `-count=200` в фоне через свой
  `run_in_background`, получил task-notification о его завершении, но его
  *собственная* сессия уже вернула финальный ответ раньше и не собрала
  результат в отчёт). Итог: агент вернул отчёт с пометкой «жду результата
  фоновой команды», без сводки. Не проблема — рабочее дерево содержало
  честную реализацию; основная сессия сама прогнала `gofmt`/`build`/`vet`/
  `test -race`/`-count=200` заново и получила полную картину. **Вывод:**
  когда отчёт кодера неполный, не считать это провалом реализации — сначала
  проверить `git diff --stat`, что реально написано, и перепрогнать проверки
  самому, а не перезапускать кодинг с нуля.
- **8-угловое ревью в параллель — быстрее и информативнее по одному
  агенту**: каждый угол вернул содержательный, различающийся набор
  кандидатов (efficiency и cross-file tracer не нашли ничего, altitude нашла
  фактическую переоценку в doc-комментарии, simplification — реальную
  избыточную ветку, line-by-line — реальный CLI-баг). Дублирование одной и
  той же находки в 2+ углах (позиционный аргумент CLI нашли и line-by-line,
  и removed-behavior угол) — снова сильный сигнал, чинить без колебаний.
- **Не каждая находка ревью достойна фикса.** Angle Reuse предложил заменить
  `recvNow` (fake_test.go) на `Receive` с заранее отменённым контекстом —
  при верификации оказалось, что это **внесло бы гонку**: `select` в Go
  случайно выбирает между двумя готовыми кейсами, так что `Receive` с уже
  отменённым `ctx` мог бы вернуть `ctx.Err()` вместо ожидающего в буфере
  пакета. Отклонено при верификации по `file:line`, не применено. Держать
  такую же дисциплину: сначала прочитать код и подтвердить, что предложенный
  фикс действительно не хуже текущего кода, а не применять совет ревью
  бездумно.

## 4. Технические решения Этапа 5, важные для следующего шага (мерж или новый Этап)

- **`FakeNetwork` — единственная точка конфигурации симулятора**, все новые
  ручки (`SetDropRate`, `Partition`/`Heal`, `SetDelay`/`SetDefaultDelay`,
  `NewFakeNetworkSeed`) висят на `*FakeNetwork`, не на отдельных `*Fake`.
  Контракт `transport.Transport` (`Send`/`Receive`/`LocalAddr`/`Close`) не
  менялся — `var _ Transport = (*Fake)(nil)` жив.
  `internal/swim`/`internal/member`/`internal/protocol` Этап 5 не трогал
  вовсе (сознательная граница, см. план §4/§7).
  Проверка в `Send`: partition → drop-rate → delay (партиция не тратит RNG,
  100%-дроп тоже — детерминизм `DropLink` не зависит от порядка розыгрышей
  на других линках).
- **CLI теперь двухкомандный** (`run`/`observe`), обратно совместим:
  `swim-discovery -addr ...` без подкоманды по-прежнему запускает узел
  (дефолт на `run`). `observe` крутит read-only печать `List.Members()` в
  отдельной горутине — не мешает probe/receive-циклам узла. Конфигурация
  таймаутов узла через CLI-флаги — по-прежнему вне scope (осознанно, план §0).
- **MVP по `docs/PLAN.md` формально закрыт этим Этапом** — следующий шаг не
  предопределён `TECHNICAL_PLAN.md` (там нет «Этапа 6»). Всё, что дальше, —
  это выбор из `docs/POST_MVP_PLAN.md` (список идей, не приоритизированный
  план) или решение остановиться на MVP.
